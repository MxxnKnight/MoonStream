## 1. Logs screen went black when scrolling up

**Symptom.** Scroll up a few lines → every log line disappears, only the
scroll-to-bottom button remains. Tapping the button brings all lines back.

**Root cause (layout, not data).** The scroll-to-bottom button was placed in the
screen `Column` *after* the list, wrapped in `Box(Modifier.fillMaxSize())`:

```kotlin
Column {
    Header(...)
    Box(Modifier.weight(1f)) { LazyColumn(...) }   // list
    if (showScrollDown) {
        Box(Modifier.fillMaxSize()) { ...button... }   // ← made the list 0dp tall
    }
}
```

A `Column` measures non-weighted children first, with the *full* remaining height
as the max constraint. `fillMaxSize()` therefore claimed the entire height, and
the weighted list Box got `0dp`. The button still drew (bottom-end aligned inside
its full-screen Box), which is why the screen looked black but interactive — and
why tapping it "fixed" things: scrolling to the bottom hides the button, the
full-screen Box leaves the layout, and the list gets its height back.

Earlier comments in that file blame the live ring buffer / eviction — that was a
real bug too (hence the snapshot), but it is **not** this one. Do not re-add a
full-size sibling next to a weighted child in a `Column`.

**Fix** — `ui/screens/LogsScreen.kt`, rewritten:
- One `Box(Modifier.weight(1f))` owns both the `LazyColumn` and the button; the
  button is a direct child with `Modifier.align(Alignment.BottomEnd)`, so it costs
  zero layout space.
- Dropped the redundant outer `Box` + unused `LocalContext`/`Toast` imports.
- Behaviour otherwise unchanged: snapshot on open, `Refresh`/`Clear`/`Copy`,
  one-shot scroll to newest, `AppLog` untouched.

## 2. "Continue watching" strip under Recently Added

**Symptom.** The strip was added (row code existed, player wrote to
`watch_progress`) but it looked broken/empty, the progress line was invisible, and
the SxxExx was not on the poster.

**What was actually wrong (four separate things).**

1. **It only reloaded by accident.** The old code refreshed on the *Activity's*
   `ON_RESUME` via `LocalLifecycleOwner`. This app swaps screens inside one
   `Activity` with a manual back stack (`MainActivity`, `when (screen)`), so
   ON_RESUME **never fires** when you come back from the player. It appeared to
   work only because `ServerScreen` left composition and was rebuilt. Any future
   nav change (or `rememberSaveable`/kept state) would freeze the strip forever.
2. **One entry per file, not per show.** `watch_progress` is keyed by
   `(mediaId, streamFileId)`, so watching E01 then E02 produced two posters of the
   same series, and both consumed the 15-row limit (the LIMIT was applied *before*
   the >10 s filter, so real candidates could be pushed out).
3. **Poster/title were snapshots.** They were copied into `watch_progress` at
   insert time; if `mediaDao().getById(mediaId)` had returned null the poster was
   blank (letter tile) until the row was recreated.
4. **SxxExx and the progress line.** The label rendered as a grey text line *under*
   the title (not the requested top-left chip), and the progress line drew nothing
   at all when `durationMs == 0` — which is exactly the state right after the row
   is created, so early entries had no line.

**Fix — three files.**

`index/db/Entities.kt` — new projection POJO:

```kotlin
data class ContinueWatchingItem(
    val mediaId: Long, val streamFileId: Long, val title: String,
    val episodeLabel: String?, val posterUrl: String?,
    val playedAt: Long, val positionMs: Long, val durationMs: Long,
)
```

`index/db/Daos.kt` — `WatchProgressDao.observeContinueWatching()`, a **Flow**
(`watch_progress LEFT JOIN media_items` with `COALESCE(m.title, wp.title)` and
`COALESCE(m.posterUrl, wp.posterUrl)`, `ORDER BY wp.playedAt DESC`). Room validates
the SQL at compile time, so a broken query fails the build — good.

`ui/screens/ServerScreen.kt` — `ContinueWatchingRow()`:
- `collectAsState(initial = emptyList())` on that Flow; Room pushes every position
  save, so **no refresh plumbing at all**. All `refreshTick` / lifecycle-observer /
  `withContext(Dispatchers.IO)` code is gone.
- `rows.filter { positionMs > 10s && (durationMs <= 0 || positionMs < durationMs * 0.9f) }`
  then `.distinctBy { it.mediaId }` (rows arrive newest-first, so the newest file
  per show wins) then `.take(10)` — computed inside `remember(rows)`.
- SxxExx is now a chip at `Alignment.TopStart` of the poster: `labelSmall`,
  semibold white text, `Black` 72 % background, 6dp corner radius, only drawn when
  `episodeLabel` is non-blank. The old text line under the title was deleted.
- Progress line is always drawn: 3dp `Black` 45 % track at the poster bottom with an
  accent fill for the played fraction (fill only when progress > 0).

**Behaviour that is intentional, not a bug** — don't "fix" these:
- Nothing appears until >10 s of playback (the insert starts at 0 s and the periodic
  saver only writes past 10 s). Testing with a 5-second play looks like nothing
  happened.
- Entries past 90 % (credits) are hidden.
- Only in-app playback is tracked; external players can't report position.
- The strip still opens **Detail** (`onOpenDetail(mediaId)`); Detail's header Play
  is the resume path (`latestForMedia`).

**Debugging if it ever looks empty again.** The player logs
`ContinueWatching: INSERTED row …` / `closed at Ns of … resume position saved` to
the Logs screen. No such line ⇒ nothing is being written (check `mediaId` /
`streamFileId` are non-zero where `AppScreen.Player` is created), which is a
different bug from anything above.

## 3. Seekbar buffer was invisible

**Symptom.** "I can't see the buffer literally." It was implemented.

**Root cause.** `PlayerScreen` draws a base track (white 25 %) and a buffer fill
(white 50 %) as `Box`es behind the Material3 `Slider`, whose `inactiveTrackColor` is
transparent. Two of the three reasons it read as invisible:
- 25 % → 50 % white on a 4dp line over a dark player is a barely perceptible step;
- the stream comes from the phone's own server/TDLib window, so
  `bufferedPosition` reaches 100 % within a second and the whole track becomes one
  flat grey with no moving edge to notice.

Geometry was never wrong: Material3 1.1.1's slider track is exactly 4dp
(`SliderTokens.ActiveTrackHeight`), the same as the drawn boxes, both centred in the
same 24dp container, and the played part is already the Slider's accent active track.

**Fix** — `ui/screens/PlayerScreen.kt`, only alphas + a comment:
- base track `White` 0.25 → **0.20**
- buffer fill `White` 0.5 → **0.62**

**If it is still too subtle on the phone**, the next step is *not* more alpha — move
the whole track into the Slider's `track` slot and delete the stacked Boxes:

```kotlin
Slider(value = …, onValueChange = …, valueRange = …,
    colors = SliderDefaults.colors(thumbColor = Accent,
        activeTrackColor = Color.Transparent, inactiveTrackColor = Color.Transparent),
    track = { _ -> /* base + buffer + played, drawn from the same lambda */ })
```

`SliderPositions` (the slot overload with `thumb`/`track`) **does exist in
material3 1.1.1** — verified in the cached artifact, so this needs no dependency
bump. It guarantees pixel-perfect alignment and can't be overdrawn.

**Also worth checking on a device:** log `player.bufferedPosition` once after
`STATE_READY`. If it stays 0, the custom TDLib/Telegram data source isn't reporting
load progress and no amount of drawing will make the bar move — that's a
`MediaSource`/`DataSource` issue, not UI.

## 4. Bottom-bar blur — deliberately NOT done

moon said leave it. For the next agent, the recorded finding (also in `AGENT.md`
history): `Modifier.blur()` in Compose 1.6.1 blurs a composable's **own** content and
only works on **Android 12+**; there is no built-in backdrop blur, and this project
already tried and reverted both Cloudy and Dimezis `BlurView` (the latter crashed on
Android 12, commit `cf1ee5a`). Haze needs Kotlin 2.x + Compose 1.7+, i.e. a real
upgrade first. Current pill is a 78 % black rounded rect with a 0.5dp white 10 %
hairline — leave it alone unless moon asks.
