## 1. Resume did not work, and the Resume button never appeared

### It is NOT the MKV container
Position saving and restoring use ExoPlayer's millisecond position, which is
container-agnostic: an MKV saves exactly like an MP4. If a file cannot actually
play (for example a 5.1 EAC3 track the Helio G96 can't decode), you get the
player error screen and the position stays 0 — that is a decode problem, not a
resume one, and it would affect MP4 with AC3 the same way.

### Root cause: the saved spot was deleted the instant you pressed play
`DetailScreen.recordWatch()` ran on every press of a Play button and did:

```kotlin
dao.deleteByStreamFile(file.id)   // ← deletes the row, position and all
dao.upsert(WatchProgressEntity(...))  // fresh row, positionMs defaults to 0
```

`recordWatch()` is fired from `playInApp()` (and `playContinue()`) at the same
moment the player opens and reads its resume point in
`LaunchedEffect(playUri, …)`. So the read raced a wipe:

- if the wipe won, the player saw 0 → started at 0:00;
- if the read won, it saw the position but the row was then zeroed anyway, so the
  5-second saver `updatePosition()` wrote over a *different* row or the next open
  had nothing to resume from;
- `savedResumePos` (what the Resume pill needs, `> 10s` and we're behind it) was
  read from that same row, so it was 0 → **button never shows**.

That also means the Continue Watching strip had nothing useful for that file
until the 10-second threshold was crossed again.

### Fix
`index/db/Daos.kt` — new `WatchProgressDao.touchOpened(...)`:

```sql
UPDATE watch_progress
   SET mediaId = :mediaId, title = :title, episodeLabel = :episodeLabel,
       posterUrl = :posterUrl, playedAt = :playedAt
 WHERE streamFileId = :streamFileId
```

It refreshes the metadata and `playedAt` but **never touches `positionMs` /
`durationMs`**. It also re-points `mediaId`, so a row orphaned by a duplicate
merge heals itself the next time the file is opened.

`ui/screens/DetailScreen.kt` — `recordWatch()` now calls `touchOpened(...)`; only
when it reports 0 rows affected (the file was never played) does it insert a fresh
row at position 0. No delete, no wipe.

### Verification (on the phone)
1. Play a file, watch ~1 minute, back out. Logs (`PLAYER`) should show
   `closed at 60s of … — resume position saved`.
2. Open the same file again. Logs must show `Resume: starting at 60s (saved spot)`
   and playback must begin there, no Resume pill needed.
3. Watch, then drag the seekbar back to the start: the Resume pill should appear
   at the bottom left (`Resume 1:00`).

If `Resume: starting at …` never logs but `closed at …resume position saved` does,
then the read is by `(mediaId, streamFileId)` while the write is by `streamFileId`
only — check that the id passed to `AppScreen.Player` matches the file the row was
written for (a re-scan re-creates `stream_files` ids).

### Related, unchanged on purpose
- `playExternal()` (the "Play with" sheet) still resets the row: an external
  player cannot report its position, so starting fresh there is correct.
- Nothing is saved under 10 s and a spot past 90 % is cleared (Kodi-style).
- Do **not** bump the DB version for this: `touchOpened` is a query, not a schema
  change.

## 2. Bottom pill capsule: drag feel, height and spacing

All in `MainActivity.kt`, the floating nav pill.

### Drag was not "perfect" because it ran a spring through a coroutine per event
The old code, on every pointer move, did `capsuleAnim.job?.cancel()` and
`pillScope.launch { pillCenterX.animateTo(fingerX, navSlideSpec) }`. A medium-low
stiffness spring that is cancelled 60–120 times a second never gets to move, so
the capsule crawled behind the finger; the coroutine churn also cost frames while
the list underneath was scrolling (low-end GPU/CPU).

Now:
- **one plain state write per event, no coroutine at all** —
  `dragPillX = cur + (finger - cur) * follow`, with `follow = 0.45f` on the first
  engaged event (so it visibly runs from its tab toward the finger instead of
  teleporting) and `0.85f` afterwards (so it sits under the finger 1:1).
- `dragPillX` is a nullable float state that *overrides* the `Animatable` while
  the finger holds the capsule; the capsule offset reads
  `dragPillX ?: pillCenterX.value`.
- On release the `Animatable` is snapped to the drag position **inside a launched
  coroutine before the override is cleared**, otherwise the capsule flashed back
  to the old tab for one frame and only then slid — the little "jump" at the end
  of a drag.
- The tab decision on release uses the **finger's** last X, not the capsule's, so
  a fast flick lands on the tab the finger is over even if the capsule's smoothed
  position is a few px behind.
- A cancelled gesture (pointer taken away mid-drag) parks the capsule back on the
  selected tab; previously the override could stay set and leave the capsule stuck
  mid-bar.

**Do not** call `pillCenterX.snapTo()` directly inside the gesture loop: it lives
in `awaitPointerEventScope`, a restricted coroutine scope, and refuses those
suspend calls (the compiler rejects it). That restriction is why the old code
went through `pillScope` in the first place.

### Position and space
The capsule height was hardcoded `47.dp` while the bar was `~48dp`, so the gap at
the bar's rounded ends depended on the system font size and the capsule could
poke out with large text. Now the bar reports its measured height
(`onGloballyPositioned { barHeightPx = it.size.height }`) and the capsule is
`barHeightPx − 6dp` (3 dp inset top and bottom), centred by
`Alignment.CenterStart`. It is always exactly inside the bar and evenly spaced at
any font scale. While the finger holds it the capsule brightens slightly (0.22 →
0.30 white) so the grab is visible.

## 3. Screen switching felt slow — faster, and cheaper on this GPU

Three places had the same transition: `MainActivity` (screens/tabs),
`LibraryScreen` (segment grid) and `SettingsScreen` (sub-pages).

What changed in all three:
- **220 ms → 165 ms** slide.
- **The full-screen `fadeIn` was removed** from the directional slide. A whole
  screen fading + moving forces an offscreen composition layer and a per-pixel
  alpha blend on top of the movement — that is the expensive half on a Helio G96,
  and at 165 ms it also looked softer/slower. Movement only. (The no-direction
  case, `dir == 0`, is fade-only and went 110 ms → 90 ms.)
- **The pill drops its backdrop blur during the switch**
  (`screenSwitching`, set for 185 ms from `LaunchedEffect(current)` in
  `MainActivity`). Haze re-captures and re-blurs the entire screen every frame;
  during a slide that work competes directly with the animation. For those 185 ms
  the pill draws a plain `Black` 80 % tint (visually the same frosted-dark look)
  and the blur returns the moment the switch lands. This is the single biggest
  win of the three.

Only the incoming screen animates (`ExitTransition.None`), so one heavy screen is
alive at a time — that part was already right, do not "improve" it by animating
both.
